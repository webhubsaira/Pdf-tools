Technical Security

iLovePDFs Security Architecture

How client-side sandboxing, zero server retention, and cryptographic principles protect your documents at every stage of the workflow.

Traditional Cloud Converters
  • Files uploaded across public internet to remote servers.
  • Stored in temporary cloud storage buckets or databases.
  • Subject to server breach, unauthorized access, or scraping.
  • Requires trust in third-party automated deletion scripts.
iLovePDFs Client Sandbox
  • Files are read into local browser RAM memory only.
  • Transformation executes via WebAssembly & JavaScript.
  • Document bytes never leave your workstation.
  • Zero retention risk: closing the tab instantly clears memory.

1. Client-Side Memory Isolation

iLovePDFs' client-ready tools utilize the browser's native JavaScript sandbox. When you drag and drop files into the interface, the browser's FileReader API reads the binary data into an isolated ArrayBuffer in active RAM.

At no point during standard client operations is an HTTP POST request or upload payload sent across the network. You can verify this at any time using your browser's Developer Tools Network Inspector.

2. Ephemeral Blob Object URLs

When iLovePDFs finishes processing a document (such as merging pages or stamping a watermark), the output Uint8Array is packaged as a local binary Blob.

The download is initiated via an ephemeral blob: URL. This URL is scoped strictly to your browser tab session and is actively revoked by our memory garbage collection lifecycle.

3. Cryptographic Hygiene & Password Protection

For tools that support password encryption or protection, user-entered passphrases are used directly to configure the document's security handler and are never transmitted or logged.

Security Disclosure

This site does not currently provide a dedicated security disclosure or inquiry channel. Do not include sensitive vulnerability details in PDF uploads or other site features.
